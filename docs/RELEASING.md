# Release Process

**Reviewed:** 2026-08-02

**Current status:** The distribution workflow is prepared, but Noter has not
published a supported binary release. Running a publication job requires an
explicit release decision after every gate below passes.

## Release outputs

The pinned dist 0.32.0 configuration plans these outputs from one source
revision:

- `.tar.xz` archives for glibc Intel Linux, Intel macOS, and Apple Silicon macOS;
- a `.zip` archive and protected per-machine MSI package for Intel Windows;
- checksum-verifying POSIX and PowerShell installers;
- a Homebrew formula;
- SHA-256 files and one unified checksum list;
- a generated third-party dependency inventory and bundled-font license in
  every binary package;
- target-specific CycloneDX 1.5 SBOMs for all four release targets; and
- GitHub artifact attestations for every published archive, installer,
  checksum, manifest, formula, and SBOM.

Attestation establishes GitHub-hosted build provenance. It is not Windows or
macOS code signing. A release must disclose the signing state plainly and must
not describe unsigned artifacts as signed.

## Required release gate

1. The version, lockfile, changelog, and release notes agree.
2. The candidate is the exact clean tip of the protected `main` branch.
3. Required CI, dependency audit, license policy, coverage, mutation, and
   documentation checks pass on that commit.
4. The complete manual platform matrix is recorded for supported Windows,
   macOS, X11, and Wayland environments.
5. Clean install, reinstall, upgrade, rollback, and uninstall checks pass as a
   standard user.
6. The complete README capture set is regenerated from the candidate and
   reviewed at 100 and 150 percent scale: identical-document Light Text and
   Markdown plus Dark, Green Screen, and Amber Screen Markdown.
7. Runtime inspection finds no unexpected network activity or sensitive logs.
8. No unresolved critical or high security or data-safety defect exists.
9. The release-candidate dogfood period and independent-user requirement in the
   roadmap are complete.

The first public artifact should remain a prerelease until the full M7 exit
criteria are met. The current workflow rejects stable version tags and accepts
only a matching prerelease version such as `0.1.0-alpha.1` committed in both
workspace packages.

Windows Installer compares only the first three numeric ProductVersion fields.
The MSI therefore uses an independent, strictly increasing three-field package
sequence while `ARPDisplayVersion` shows the exact Noter SemVer. Increment the
package sequence for every published MSI, never reuse it for a different build,
and update the validator expectation in the same reviewed change. This keeps
major upgrades and downgrade refusal deterministic without enabling ambiguous
same-version upgrades.

## Local preflight

Run the normal repository gates first, then verify the reviewed distribution
configuration and plan with the exact pinned dist executable:

```text
python scripts/check_release_config.py
dist plan --tag v<VERSION>
```

The checked-in workflow and MSI definition intentionally harden cargo-dist's
generated templates. The validator replaces the generator's drift check: it
enforces least-privilege workflow tokens, immutable action and bootstrap-tool
pins, complete SBOM and attestation paths, permanent MSI identities, a protected
Program Files destination, and a byte-exact Apache-2.0 license sidecar. Do not
regenerate either file in place without reviewing and reapplying those controls.

The plan must include every intended target, both installer scripts, checksums,
the source archive, all four target-specific SBOMs, third-party notices, and
native Windows packaging. The SBOMs are cargo-dist extra artifacts generated by
the bounded repository script; built-in generic SBOM generation stays disabled
so the manifest cannot name a file that differs from the published set. Review
dependency duplication, dynamic linkage, package metadata, the reviewed release
notes, and every signing or platform-support warning.

The third-party notice is generated by
`python scripts/generate_third_party_licenses.py`. The bounded renderer consumes
frozen cargo-about JSON, validates every component mapping, and scans the legal
files packaged in each checksum-locked third-party source tree. It keeps declared
SPDX expressions separate from the union of license, copyright, and notice
texts, ignores absolute source paths, normalizes line endings, sorts every
component and relative source mapping, and rejects unsafe or unbounded input.
Discovery excludes conventional non-runtime trees and source-code lookalikes.
It recognizes compact third-party notice conventions and bundled font license
sidecars that do not use a generic license filename.
Legal-file reads reject links, Windows reparse points, hard links, directory
replacement, and observed concurrent mutation before contributing any text.
This distinction follows the Cargo manifest model for
[`license` and `license-file`](https://doc.rust-lang.org/cargo/reference/manifest.html#the-license-and-license-file-fields)
and SPDX guidance that copyright notices are not represented by short-form
[license identifiers](https://spdx.dev/learn/handling-license-info/#copyright-notices).
CI regenerates and byte-compares the result on Linux, with a fail-closed
diagnostic capped at 64 KiB.

The release validator binds the complete release workflow, CI workflow, WiX
authoring source, and cross-platform CI test job to reviewed SHA-256 digests in
addition to checking their semantics. Its CI invocation uses an explicit
isolated Python shell so inherited run defaults cannot suppress the validator.
Any intentional change requires a security review of the affected publication,
installation, or native-test path before updating the corresponding digest in
`scripts/check_release_config.py`.

## Hosted dry run

From the clean candidate commit, dispatch the `Release` workflow with the input
`dry-run`. That input builds and uploads temporary workflow artifacts but cannot
run the host, attestation, or GitHub Release jobs. Inspect every archive and
installer from the completed run on clean target systems.

## Publication

Publication is intentionally separate from ordinary CI. After explicit release
approval, dispatch the `Release` workflow from the exact candidate commit with
the matching prerelease `v<VERSION>` input. The workflow refuses publication
outside `main`, marks the GitHub release as a prerelease, and creates it only
after all platform and global artifact jobs succeed. Its release notes direct
users to download an artifact before executing it and verify GitHub attestation,
checksums, and the exact-tag installation guide.

SBOM generation treats only the three exact legacy slash-separated license
spellings present in upstream package metadata as named values. Cargo Deny and
the source-license inventory remain the enforcement and notice-preservation
gates for those dependencies.

Do not add a statically linked target such as musl until its non-Cargo runtime
components, license notices, linkage evidence, and SBOM representation are part
of the same validated release payload.

After publication, verify the tag target, release status, manifest, checksums,
SBOM, attestations, installer behavior, and version output from newly installed
artifacts. Record the release URL and evidence commit in the changelog and
roadmap. Keep failed artifacts private and preserve logs needed to diagnose a
failed publication.
